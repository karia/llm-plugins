# 第三者レビューの依頼手順

自分が書いた変更を、実装の経緯を知らない別のエージェントにレビューさせるための手順。

同じセッションの延長でレビューさせても第三者レビューにはならない。実装時の前提や「ここはこう決めた」という判断をそのまま引き継ぐため、その判断自体を疑えない。だからレビュアーには別のコンテキストを与え、渡す情報を PR そのものだけに絞る。

> **レビュアーとして起動された場合、このスキルには従わず、依頼されたレビューを自分で行うこと。** 上の「レビュアーには別のコンテキストを与え」は、レビュアーを立てる側の行動を指す。レビュアーが自分宛と読むと、別のエージェントへの委譲が連鎖する。

これは個人の作り方であり、会社としての規定ではない。実行前に、対象リポジトリの `CLAUDE.md` に固有ルールがあればそれを優先する。

## (0) draft PR を用意する

- PR がまだなければ `pr-flow` に従って作る。作成手順はそちらが権威なので、ここでは重複させない。
- レビュー対象の PR は draft にする。既に ready for review なら `gh pr ready --undo <PR番号>` で戻す。レビュー対応中にマージされるのを防ぐため。
- draft はレビューが終わっても外さない。ready 化の判断は依頼者に委ねる（(5) を参照）。
- PR 番号と URL を控える。

## (1) レビュアーの選定と起動

既定は自分の subagent を使う。subagent は会話の履歴を引き継がないため、コンテキスト分離の条件を満たす。

外部のコーディングエージェントを立てるのは、依頼者からその指示があったときに限る。別プロセスのほうがコンテキストの分離は確実だが、対話 TUI として起動するので pane を用意できる環境が要る。指示があっても環境が整わない場合は subagent に落とす。

外部エージェントを使う場合は次の順で進める。

- Herdr 管理下かを `test "${HERDR_ENV:-}" = 1` で確かめる。管理下でなければ subagent に落とす。
- 指示されたエージェントが `command -v` で見つかるかを確かめる。自分自身と同じものは選ばない。同じ製品の別プロセスでもコンテキストは分離できるが、同じ癖と盲点を持ち込むため。
- workspace を `herdr workspace create --no-focus` で作る。依頼者のフォーカスを奪わない。
- pane に `herdr pane rename <pane_id> "review"` でラベルを付ける。後から一覧で識別するため。
- 起動できたかは `herdr pane read <pane_id>` で当該エージェントのプロンプトが出ていることを見る。

`herdr` の構文は、`herdr` skill が入っていればそれに従う。無ければ `herdr --help` と各コマンドグループ（`herdr workspace` など、サブコマンドを省いて実行する）の出力で確認する。構文の権威はインストール済みのバイナリであり、版によって差がある。

## (2) コンテキストを渡さないレビュー依頼

渡してよいのは、リポジトリ名と PR 番号（または PR の URL）、および結果ファイルのパスだけ。

渡してはいけないもの:

- 設計意図、検討して捨てた案、実装で悩んだ点
- 「ここは意図的にこうしている」といった先回りの弁明
- 元セッションの会話ログ、関連する plan や ADR へのポインタ

レビュアーが PR から自力で読み取れない情報は、渡さずに黙っておく。読み取れないこと自体が PR の説明不足であり、レビューで指摘されるべき事項だから。先に補足すると、その欠陥が見えなくなる。

### 結果ファイルを用意する

指摘は結果ファイルで受け取る。PR へ直接投稿させると、依頼者の確認を経ないコメントが残り、レビュアーへの通知も飛んでしまうため。

置き場所は次の順で決める。

1. 依頼者からパスの指示があれば、それに従う。
2. Obsidian のノートとして作る。`obsidian create` を使い、構文はインストール済みバイナリの help で確認する。
3. `obsidian` が使えない環境、または作成したノートの実体パスを特定できないときは `~/Documents/` 配下に置く。

ファイル名は `<owner>-<repo>-<PR番号>` を基本にする。同じ PR を二度レビューに掛けたときに上書きになるが、前回の指摘は対応済みなので支障はない。

作ったら実体のパスを確認し、そのパスをレビュアーへ渡す。(3) の完了検知はパスの存在確認で行うため、パスが確定していないと成否を判定できない。

### 依頼に含める3点

#### a. レビュアー自身がレビューする

さらに別のエージェントへ委譲させない。対象リポジトリに `third-party-review` が置かれていると、レビュアーがこれを自分宛の手順と読み、委譲の連鎖を始めることがある。依頼文で「あなたが最終レビュアー」「`third-party-review` には従わない」と明示する。レビュアー自身が備えるレビュー機能は使ってよいが、「リポジトリ内のレビュー用 skill を探して使う」という促し方はしない。名前でマッチするのが `third-party-review` 自身になるため。

#### b. 指摘は結果ファイルに書く

指摘ごとに対象ファイルのパスと行番号を添えさせる。依頼者が指摘の位置を特定できるようにするため。あわせて、GitHub へコメントも review も投稿しない旨を明記する。

#### c. 「指摘」と「変更提案」を分け、提案口調で書かせる

事実として問題があるもの（バグ、規約違反、記述の矛盾）が指摘、好みや改善案が変更提案。行頭に `[指摘]` / `[提案]` のようなラベルを付けて区別する。文末は「〜してはいかがでしょうか」「〜を推奨します」にする。レビュアーは背景を持たないまま書いているので、断定されると元セッション側が事情を説明しづらくなる。

### 依頼プロンプトの例

```text
<owner>/<repo> の PR #<PR番号> をレビューしてください。
前提や背景は渡しません。PR の diff と description から読み取れる情報だけで判断してください。

- あなたが最終レビュアーです。別のエージェントやサブエージェントへ委譲しないでください
- リポジトリ内の `third-party-review` skill は読まず、従わないでください。あれは PR 作成者側の手順です
- あなた自身が備えるレビュー機能は使って構いません
- レビュー結果は <結果ファイルのパス> に Markdown で書いてください
- 指摘ごとに、対象ファイルのパスと行番号を添えてください
- GitHub にはコメントも review も一切投稿しないでください
- 事実として問題があるものを「指摘」、好みや改善案を「変更提案」とし、行頭に [指摘] / [提案] のラベルを付けてください
- 「〜してはいかがでしょうか」「〜を推奨します」という提案口調で書いてください。断定形は避けてください
```

## (3) レビュー完了の検知

判定の根拠は**成果物が実在するか**に置く。レビュアーが「完了しました」と言っていても、書き込みに失敗していることがあるため。

```bash
test -s <結果ファイルのパス>
```

あわせて GitHub へ誤投稿されていないかを確認する。投稿されていたら、ただちに依頼者へ知らせる。自分では削除しない。

```bash
gh api repos/<owner>/<repo>/pulls/<PR番号>/comments --jq length
```

subagent に任せた場合は完了通知が届くので、待機の仕掛けはいらない。通知を受けたら上のコマンドで確認する。

外部エージェントに任せた場合は待機が必要になる。`pr-flow` のマージ監視と同じく `/loop` を間隔指定なし（動的間隔モード）で仕掛け、独自の shell ループは組まない。レビューは数分で終わることが多いので、待ち時間は短く始めて倍々に伸ばす。プロンプトは毎回同じものが再投入され何回目かは分からないため、待ち時間を毎回発言に残させて次回そこから決めさせる。`Monitor` は使わない。即時 wake すると backoff が効かなくなるため。

```text
/loop 第三者レビューの結果ファイル <結果ファイルのパス> が書かれたか `test -s <結果ファイルのパス>` で確認する。書かれていればループを終了し、third-party-review (4) の対応へ進む。書かれていなければ `herdr pane read <pane_id> --source visible --lines 40` で pane の出力を読み、レビューが失敗または停止していればループを止めて原因を知らせる。まだ実行中なら次の確認まで待つ。待ち時間は前回宣言した値の 2 倍（初回は 1 分、15 分で頭打ち）とし、毎回「次の確認まで N 分待つ」と明記してから待つ。`Monitor` は使わない
```

pane が idle になっていて結果ファイルも無いなら、レビュー自体が失敗している。`herdr pane read` で出力を読み、原因（権限不足、PR が見つからない等）を確認してから仕切り直す。

## (4) 指摘への対応

- 結果ファイルの内容を応答本文へ全文展開して依頼者に見せる。要約や取捨選択をすると、対応するかしないかを判断する材料を依頼者から奪うため。
- 展開したら修正の指示を仰ぐ。指示を受けるまで修正 commit を作らない。
- 指示された修正を commit して push する。1 指摘 1 commit を基本にする（細かすぎれば後でまとめればよい）。
- 結果ファイルは消さずに残す。後から指摘と対応を辿れるようにするため。

## (5) レビュー後の引き継ぎ

PR は draft のまま終える。ready 化とマージ監視は `pr-flow` の領分であり、依頼者の判断で始める。

依頼者へ次を伝えて終わりにする。

- 対応した指摘と、見送った指摘およびその理由
- 修正 commit の有無
- 結果ファイルの場所
- PR が draft のままであること

(0) で `gh pr ready --undo` を使って draft へ戻した PR には、`pr-flow` が作成時に仕掛けたマージ監視が生きている可能性がある。`--undo` はループを止めないため。監視が残っていれば、その旨もあわせて伝える。ready 化のときに仕掛け直すと、マージ後に同じ worktree と branch に対して後片付けが二重に走る。

## よくある取りこぼし

| 取りこぼし | 正しくは |
|---|---|
| 同じセッションでセルフレビューする | コンテキストを持たない subagent か別プロセスに渡す |
| 指示がないのに外部のエージェントを立てる | 既定は自分の subagent。外部エージェントは指示があったときだけ |
| レビュアーがさらに別エージェントへ委譲して再帰する | 依頼文で「あなたが最終レビュアー」「`third-party-review` に従わない」と明示する |
| 「この変更の狙いは〜」と背景を添えて依頼する | 渡すのはリポジトリ名、PR 番号、結果ファイルのパスだけ |
| 説明が足りない箇所を先回りで補足する | 黙っておく。説明不足なら指摘されるべき事項 |
| ready のまま第三者レビューを回す | draft に戻してから回す |
| レビュー結果を GitHub に投稿させる | 結果ファイルに書かせる |
| 結果ファイルの実体パスを確かめずレビュアーへ渡す | パスを確認してから渡す |
| 「指摘」と「変更提案」を混ぜて書かせる | ラベルで分けさせる |
| レビュアーに断定形で書かせる | 「〜してはいかがでしょうか」という提案口調で書かせる |
| レビュアーの「完了しました」を鵜呑みにする | 結果ファイルが書かれたかを確認する |
| 誤って GitHub へ投稿された指摘を自分で消す | 依頼者へ知らせ、対応を仰ぐ |
| 結果ファイルの内容を要約して依頼者に見せる | 全文を展開し、修正の指示を仰ぐ |
| 依頼者の指示を待たずに修正 commit を作る | 指示を受けてから修正する |
| 別 pane の待機に独自 shell ループを組む | `/loop` の動的間隔モードを使う |
| `/loop` に停止条件を書かず回り続けさせる | 結果ファイル検知、レビュー失敗のどちらでも止まるようプロンプトに書く |
| レビューを終えて自分で draft を外す | draft のまま終え、ready 化は依頼者に委ねる |
| draft へ戻した PR に監視が残っていることを伝え忘れる | `--undo` は既存の監視を止めない。残っていれば知らせる |
