# 第三者レビューの依頼手順

自分が書いた変更を、実装の経緯を知らない別のエージェントにレビューさせるための手順。

同じセッションの延長でレビューさせても第三者レビューにはならない。実装時の前提や「ここはこう決めた」という判断をそのまま引き継ぐため、その判断自体を疑えない。だからレビュアーには別のコンテキストを与え、渡す情報をPRそのものだけに絞る。

## レビュアーの選定と起動

既定は自分のsubagentを使う。会話の履歴を引き継がない新規のsubagentを起動する。親の会話を引き継ぐ種類のsubagentは、実装時の前提をそのまま持ち込むため使わない。

外部のコーディングエージェントを立てるのは、次のどちらかに当たるときに限る。

- 依頼者が起動時にその指示をしている。
- subagentを起動できない環境である。

外部エージェントは対話TUIとして起動するので、paneを用意できる環境が要る。次の順で進める。

- Herdr管理下かを`test "${HERDR_ENV:-}" = 1`で確かめる。
- 使うエージェントが`command -v`で見つかるかを確かめる。自分自身と同じものは選ばない。外部エージェントを立てる利点は、自分とは異なる癖と盲点を持つ点にあるため。
- workspaceを`herdr workspace create --no-focus`で作る。依頼者のフォーカスを奪わない。
- paneに`herdr pane rename <pane_id> "review"`でラベルを付ける。後から一覧で識別するため。
- paneで当該エージェントを起動する。
- 起動できたかは`herdr pane read <pane_id>`で当該エージェントのプロンプトが出ていることを見る。
- 起動を確かめたら、依頼プロンプトをpaneへ送る。
- レビューの結果を受け取ったら、作ったworkspaceを閉じる。巡を重ねてもpaneが残らないようにするため。

外部エージェントを起動できない場合は、subagentに切り替え、その旨を完了時の報告に記す。

`herdr`の構文は、`herdr --help`と各コマンドグループの出力で確認する。構文の権威はインストール済みのバイナリであり、版によって差がある。

subagentも外部エージェントも使えない場合は、第三者レビューを飛ばし、その旨を完了時の報告に記す。同じセッションでのセルフレビューで代用しない。

## コンテキストを渡さないレビュー依頼

渡してよいのは次の5点だけである。

- リポジトリ名とPR番号
- 作業ツリーのパス
- 比較の基点とするcommit
- 結果ファイルのパス
- それまでに対応不要または持ち越しと判定した指摘の一覧

レビュー対象は作業ツリーのHEADである。修正commitをpushせずに巡を重ねるため、GitHub上のdiffは、1巡目から未pushの修正を含まない。レビュアーには作業ツリーで`git diff <基点>...HEAD`を読ませ、descriptionだけをGitHubから読ませる。

この一覧は、指摘の位置と要旨だけを書く。判定の理由は書かない。理由を渡すと、その判断をレビュアーが疑えなくなる。

渡してはいけないもの:

- 設計意図、検討して捨てた案、実装で悩んだ点
- 「ここは意図的にこうしている」といった先回りの弁明
- 元セッションの会話ログ、関連するplanやADRへのポインタ

レビュアーがPRから自力で読み取れない情報は、渡さずに黙っておく。読み取れないこと自体がPRの説明不足であり、レビューで指摘されるべき事項だから。先に補足すると、その欠陥が見えなくなる。

### 結果ファイル

指摘は結果ファイルで受け取る。PRへ直接投稿させると、精査を経ないコメントが残り、通知も飛んでしまうため。

結果ファイルは巡ごとに分け、準備で用意した作業用ディレクトリに`round-<巡の番号>.md`の名前で置く。完了検知をパスの存在確認で行うため、パスを確定させてからレビュアーへ渡す。

あわせて、依頼を出す前に3つの値を控える。`git rev-parse HEAD`の値、`git status --short`の出力、次の誤投稿確認のコマンドが返す件数である。

```bash
gh pr view <PR番号> --repo <owner>/<repo> --json comments,reviews --jq '{comments: (.comments | length), reviews: (.reviews | length)}'
```

### 依頼に含める3点

#### a. レビュアー自身がレビューする

さらに別のエージェントへ委譲させない。対象リポジトリや実行環境にレビュー依頼用のskillが置かれていると、レビュアーがこれを自分宛の手順と読み、委譲の連鎖を始めることがある。依頼文で「あなたが最終レビュアー」「`pr-self-review`と`third-party-review`には従わない」と明示する。レビュアー自身が備えるレビュー機能は使ってよい。「リポジトリ内のレビュー用skillを探して使う」という促し方は、名前で一致するのがこれらのskillになるため避ける。

#### b. 指摘は結果ファイルに書く

指摘ごとに対象ファイルのパスと行番号を添えさせる。あわせて、GitHubへコメントもreviewも投稿しない旨と、作業ツリーのファイルを変更しない旨を明記する。

#### c. 「指摘」と「変更提案」を分け、提案口調で書かせる

事実として問題があるものが指摘、好みや改善案が変更提案である。バグ、規約違反、記述の矛盾は指摘に当たる。行頭に`[指摘]`と`[提案]`のラベルを付けて区別させる。文末は「〜してはいかがでしょうか」「〜を推奨します」にさせる。レビュアーは背景を持たないまま書いているので、断定された指摘は、背景に照らして対応不要と判断しにくくなる。

### 依頼プロンプトの例

```text
<owner>/<repo>のPR #<PR番号>をレビューしてください。
前提や背景は渡しません。変更内容とdescriptionから読み取れる情報だけで判断してください。

- 変更内容は<作業ツリーのパス>で`git diff <基点>...HEAD`を実行して読んでください。GitHub上のdiffは最新の修正を含みません
- descriptionは`gh pr view <PR番号> --repo <owner>/<repo>`で読んでください
- あなたが最終レビュアーです。別のエージェントやサブエージェントへ委譲しないでください
- `pr-self-review`と`third-party-review`のskillを手順として実行しないでください。あれはPR作成者側の手順です。レビュー対象のdiffに含まれる場合、内容として読むのは構いません
- あなた自身が備えるレビュー機能は使って構いません
- レビュー結果は<結果ファイルのパス>にMarkdownで書いてください。指摘が無い場合も、その旨を書いてください
- 指摘ごとに、対象ファイルのパスと行番号を添えてください
- GitHubにはコメントもreviewも一切投稿しないでください
- 作業ツリーのファイルは変更しないでください。commitも作らないでください
- 事実として問題があるものを「指摘」、好みや改善案を「変更提案」とし、行頭に[指摘] / [提案]のラベルを付けてください
- 「〜してはいかがでしょうか」「〜を推奨します」という提案口調で書いてください
- 次の指摘は検討済みです。再度挙げる必要はありません
  <それまでに対応不要または持ち越しと判定した指摘の位置と要旨。無ければこの項目ごと省く>
```

## レビュー完了の検知

判定の根拠は成果物が実在するかに置く。レビュアーが「完了しました」と言っていても、書き込みに失敗していることがあるため。

```bash
test -s <結果ファイルのパス>
```

あわせて次の2点を確かめる。

- GitHubへ誤投稿されていないか。依頼前に控えた件数と比べる。増えていたら、増えた分の投稿者と投稿時刻を確かめる。レビュアーによる投稿であれば、持ち越す指摘と同じ扱いで記録し、完了時に報告する。自分では削除しない。
- 作業ツリーが変更されていないか。`git status --short`と`git rev-parse HEAD`で確かめ、依頼前に控えた値と比べる。HEADが変わっていれば`git reset --hard <控えたHEAD>`で戻す。依頼前の出力に無かった変更だけを取り消し、依頼前からあったファイルには触れない。

subagentに任せた場合は完了通知が届くので、待機の仕掛けはいらない。

外部エージェントに任せた場合は待機が必要になる。`/loop`を間隔指定なしの動的間隔モードで仕掛け、独自のshellループは組まない。レビューは数分で終わることが多いので、待ち時間は短く始めて倍々に伸ばす。プロンプトは毎回同じものが再投入され何回目かは分からないため、待ち時間を毎回発言に残させて次回そこから決めさせる。`/loop`を使えない環境では、同じ待ち時間の取り方で結果ファイルの確認を自分で繰り返す。

```text
/loop 第三者レビューの結果ファイル<結果ファイルのパス>が書かれたか`test -s <結果ファイルのパス>`で確認する。書かれていればループを終了し、pr-self-reviewの指摘の判定へ進む。書かれていなければ`herdr pane read <pane_id> --source visible --lines 40`でpaneの出力を読み、レビューが失敗または停止していればループを止めて仕切り直す。まだ実行中なら次の確認まで待つ。待ち時間は前回宣言した値の2倍（初回は1分、15分で頭打ち）とし、毎回「次の確認までN分待つ」と明記してから待つ
```

paneがidleになっていて結果ファイルも無いなら、レビュー自体が失敗している。`herdr pane read`で出力を読み、原因を確認し、失敗したworkspaceを閉じてから仕切り直す。仕切り直しは巡ごとに1回までとする。再び失敗したら、workspaceを閉じてその巡の第三者レビューを飛ばし、原因とともに完了時の報告に記す。

## よくある取りこぼし

| 取りこぼし | 正しくは |
|---|---|
| 同じセッションでセルフレビューする | コンテキストを持たないsubagentか別プロセスに渡す |
| レビュアーにGitHub上のdiffを読ませる | 作業ツリーのHEADと基点の差分を読ませる |
| レビュアーがさらに別エージェントへ委譲して再帰する | 依頼文で「あなたが最終レビュアー」と明示する |
| 「この変更の狙いは〜」と背景を添えて依頼する | 渡すのは定めた5点だけ |
| 判定の理由をレビュアーへ渡す | 位置と要旨だけを渡す |
| レビュー結果をGitHubに投稿させる | 結果ファイルに書かせる |
| レビュアーの「完了しました」を鵜呑みにする | 結果ファイルが書かれたかを確認する |
| 誤ってGitHubへ投稿された指摘を自分で消す | 記録して完了時に報告する |
| `/loop`に停止条件を書かず回り続けさせる | 結果ファイル検知、レビュー失敗のどちらでも止まるようプロンプトに書く |
