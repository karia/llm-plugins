# 第三者レビューの依頼手順

自分が書いた変更を、実装の経緯を知らない別のエージェントにレビューさせるための手順。

同じセッションの延長でレビューさせても第三者レビューにはならない。実装時の前提や「ここはこう決めた」という判断をそのまま引き継ぐため、その判断自体を疑えない。だからレビュアーには別のコンテキストを与え、実装の経緯と弁明を渡さない。

一方で、評価の基準は渡す。基準が無いと、レビュアーは重要度を測れず、文面だけで確かめられる記述の食い違いや例外経路の列挙に向かう。

## レビュアーの起動

会話の履歴を引き継がない新規のsubagentを起動する。親の会話を引き継ぐ種類のsubagentは、実装時の前提をそのまま持ち込むため使わない。

subagentを起動できない環境では、第三者レビューを飛ばし、その旨を完了時の報告に記す。同じセッションでのセルフレビューで代用しない。

## 渡す情報

渡してよいのは次のものだけである。

- リポジトリ名とPR番号
- 作業ツリーのパスと、比較の基点とするcommit
- 結果ファイルのパス
- 評価の基準。成果物の種類と読み手、求める水準
- 2巡目以降は、前の巡の結果ファイルのパスと、前の巡を始めたときのHEAD

レビュー対象は作業ツリーのHEADである。修正commitをpushせずに巡を重ねるため、GitHub上のdiffは未pushの修正を含まない。

渡してはいけないもの:

- 設計意図、検討して捨てた案、実装で悩んだ点
- 「ここは意図的にこうしている」といった先回りの弁明
- 指摘を見送った理由
- 元セッションの会話ログ、関連するplanやADRへのポインタ

評価の基準を除き、レビュアーがPRから自力で読み取れない情報は、渡さずに黙っておく。読み取れないこと自体がPRの説明不足であり、レビューで指摘されるべき事項だから。

## 結果ファイル

指摘は結果ファイルで受け取る。PRへ直接投稿させると、精査を経ないコメントが残り、通知も飛んでしまうため。

結果ファイルは巡ごとに分け、準備で作った作業用ディレクトリに`round-<巡の番号>.md`の名前で置く。

依頼を出す前に、作業ツリーの`git rev-parse HEAD`と`git status --short`、次のコマンドが返す件数を控える。

```bash
gh pr view <PR番号> --repo <owner>/<repo> --json comments,reviews --jq '{comments: (.comments | length), reviews: (.reviews | length)}'
```

## 依頼プロンプト

### 1巡目

```text
<owner>/<repo>のPR #<PR番号>をレビューしてください。
実装の経緯は渡しません。変更内容とdescriptionから読み取れる情報と、次の評価の基準で判断してください。

- 成果物の種類と読み手: <例: LLMエージェントが読む手順書>
- 求める水準: <例: 個人用の道具で、通常の使い方で壊れなければよい>

- 変更内容は<作業ツリーのパス>で`git diff <基点>...HEAD`を実行して読んでください。GitHub上のdiffは最新の修正を含みません
- descriptionは`gh pr view <PR番号> --repo <owner>/<repo>`で読んでください
- あなたが最終レビュアーです。別のエージェントやサブエージェントへ委譲しないでください
- `pr-self-review`と`third-party-review`のskillを手順として実行しないでください。レビュー対象のdiffに含まれる場合、内容として読むのは構いません
- レビュー結果は<結果ファイルのパス>にMarkdownで書いてください
- GitHubにはコメントもreviewも投稿しないでください。作業ツリーのファイルも変更しないでください
- 最初に判定を書いてください。このままマージしてよいか、です
- 挙げる問題は、マージを止める理由になるものだけにしてください。5件までです
- 問題ごとに、位置（ファイルのパスと行番号）、通常の使い方でどう壊れるか、その被害、実際に確かめたか読んで推測したかを書いてください
- マージを止めない気づきは、末尾に3件まで、1行ずつ書いてください
- 問題が無ければ「問題なし」と書いてください。それも正常な結果です
```

### 2巡目以降

1巡目の依頼から、評価の基準と注意事項はそのまま残し、レビューの範囲だけを次のように差し替える。

```text
<owner>/<repo>のPR #<PR番号>の修正を確認してください。
前回のレビュー結果は<前の巡の結果ファイルのパス>にあります。前回の後の修正は、<作業ツリーのパス>で`git diff <前の巡を始めたときのHEAD>..HEAD`を実行して読んでください。

確かめるのは次の2点だけです。それ以外の箇所はレビューしないでください。

- 前回挙がった問題が解消したか。直されていない問題は作成者が見送ったものなので、挙げ直さないでください
- この修正によって新しく壊れた所が無いか
```

## レビュー完了の検知

subagentの完了通知を受けたら、結果ファイルが書かれたかを`test -s <結果ファイルのパス>`で確かめる。レビュアーが「完了しました」と言っていても、書き込みに失敗していることがあるため。

あわせて次の2点を確かめる。

- GitHubへ誤投稿されていないか。依頼前に控えた件数と比べる。増えていたら完了時に報告する。自分では削除しない。
- 作業ツリーが変わっていないか。依頼前に控えたHEADと`git status --short`の出力と比べる。変わっていたら、増えた変更を取り消してから次へ進み、完了時に報告する。

結果ファイルが無いか空なら、レビュー自体が失敗している。仕切り直しは巡ごとに1回までとする。再び失敗したら、その巡の第三者レビューを飛ばし、完了時に報告する。

## よくある取りこぼし

| 取りこぼし | 正しくは |
|---|---|
| 同じセッションでセルフレビューする | 会話の履歴を持たないsubagentに渡す |
| レビュアーにGitHub上のdiffを読ませる | 作業ツリーのHEADと基点の差分を読ませる |
| 「この変更の狙いは〜」と背景を添えて依頼する | 渡すのは定めたものだけ |
| 評価の基準を渡さずに依頼する | 成果物の種類、読み手、求める水準を渡す |
| 気づいた点を全て挙げさせる | 判定と、マージを止める問題だけを5件まで書かせる |
| 2巡目以降も全体をレビューさせる | 前回の問題の解消と、修正で壊れた所だけを確かめさせる |
| レビュー結果をGitHubに投稿させる | 結果ファイルに書かせる |
| レビュアーの「完了しました」を鵜呑みにする | 結果ファイルが書かれたかを確認する |
