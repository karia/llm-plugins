# PRセルフレビューの手順

自分が書いたPRに3種類のレビューを順に掛け、指摘を自分で判定して直し、直すべき指摘が出なくなったらpushするまでの手順。

1. 成果物の検査
2. 第三者レビュー
3. プロンプト監査

成果物の検査の基準、第三者レビューの手順、文章の規範は`references/`に収めてある。

> **レビュアーとして起動された場合、このスキルには従わず、依頼されたレビューを自分で行うこと。** この手順はPRの作成者が使うものであり、レビュアーが自分宛と読むと、別のエージェントへの委譲が連鎖する。

実行前に、対象リポジトリの`CLAUDE.md`や`AGENTS.md`に固有ルールがあればそれを優先する。

## 進め方の原則

- 完走をゴールにする。開始から完了時の報告まで、依頼者への質問を挟まない。
- 指摘を直すかどうかは自分で決める。既定は「直さない」であり、判定は「指摘の判定」に従う。
- 修正は1件につき1commitにする。pushは完了処理まで行わない。
- 文章を直すときは`references/writing-style.md`に従う。
- 手順に無い事態や進められなくなる障害に当たったら、依頼者の作業と履歴を壊さない側を選んで先へ進み、完了時に報告する。

## (0) 準備

- 対象のPRを特定する。引数にPR番号かURLがあればそれを使い、無ければ現在のbranchのPRを`gh pr view`で探す。
- PRの情報を控える。`state`が`OPEN`でなければ終了する。

  ```bash
  gh pr view <PR番号> --json number,url,state,isDraft,baseRefName,headRefName
  ```

- 作業用ディレクトリを`mktemp -d`で作る。レビュー結果と判定の記録をここに置く。
- `git fetch`の後、localの`<head branch>`と`origin/<head branch>`のうち先行している方を起点にする。分岐していればpushできないため、その旨を伝えて終了する。
- 起点から作業ツリーを`git worktree add --detach <パス> <起点>`で作り、そこへ移動する。依頼者の作業ツリーと未コミット変更には触れない。置き場所は、実行環境に定めがあればそれに従い、無ければ作業用ディレクトリの下にする。
- 3つのcommitを控える。
  - **開始commit**：`origin/<head branch>`の値。これより後が未pushのcommitになる。
  - **開始時のHEAD**：起点の値。開始commitからここまでは依頼者のcommitであり、完了処理でまとめない。
  - **基点**：`git merge-base HEAD origin/<base branch>`の値。PRの差分はここからHEADまでになる。
- PRがready for reviewなら`gh pr ready --undo <PR番号>`でdraftに戻す。レビュー中にマージされるのを防ぐため。完了処理で元に戻す。
- 第三者レビューに渡す評価の基準を、PRと対象リポジトリから決める。成果物の種類と読み手、求める水準である。決めきれなければ「通常の使い方で壊れなければよい」とする。

## (1) 成果物の検査

`references/sanitize.md`の基準でPRを検査し、見つけたものを「指摘の判定」に従って直す。

- diffの行は、ファイルを直してcommitする。
- titleとdescriptionは`gh pr edit`で直す。commitは発生しないが、修正1件として数える。
- push済みのcommitのメッセージに残る名残は直さず、持ち越す。直すにはpush済みの履歴を書き換えることになるため。
- 未pushのcommitのメッセージに残る名残は記録し、完了処理で直す。

## (2) 第三者レビュー

`references/third-party-review.md`に従ってレビュアーを立て、結果ファイルを受け取る。受け取った指摘を「指摘の判定」に従って判定し、直すべきものを直す。

## (3) プロンプト監査

PRの差分にLLM向けのプロンプトが含まれる場合だけ実行する。次のものが該当する。

- system promptやprompt template
- skillやagentの定義
- `CLAUDE.md`や`AGENTS.md`のようなエージェント向けの指示ファイル
- toolの説明文

該当する場合は、`claude-api` skillを引数`prompt-audit`で実行し、差分に含まれるプロンプトを監査する。出た指摘を「指摘の判定」に従って判定し、直すべきものを直す。`claude-api` skillを使えない環境では、このステップを飛ばす。

## 指摘の判定

### 直すかどうか

レビューは細部まで挙げてくるが、全てを直すと成果物は膨らみ、修正が次の指摘を生む。そのため既定を「直さない」とし、次の両方を満たす指摘だけを直す。

- 主張を自分で確かめられた。コマンドを実行するか、公式ドキュメントで確かめる。レビュアーが読んで推測しただけの指摘は、確かめるまで事実として扱わない。
- 直す費用に見合う。手順書やプロンプトでは、書き足した一文が毎回読まれる負担になり、新しい食い違いの種にもなる。まれな経路のために条件や説明を書き足す修正は見送る。実行者が状況から判断できることは書かない。

判定は、その巡の指摘を全て並べてから行う。同じ機能に3件以上の指摘が集まったら、個別に直す前に、その機能を削るか単純にできないかを考える。

見送りは正常な結果である。見送った指摘は、位置と要旨、理由を記録する。

### 持ち越すもの

| 指摘 | 扱い |
|---|---|
| 仕様の不足や仕様の誤りで、コードの修正では解決しない | 直さず、持ち越して報告する |
| PRの目的から外れ、このPRの前提にもならない | 直さず、持ち越して報告する |
| PRの目的から外れるが、このPRの前提になる | 上の基準で判定し、直すならこのPRで直す |

判定の根拠は、PRの目的と対象リポジトリの規約、公式ドキュメント、Web検索の順に探す。どれでも決まらない指摘は、仕様の問題として持ち越す。

### 修正とcommit

- 対象リポジトリにテストやlinterがあれば実行し、修正で新たに失敗するものが無いことを確かめてからcommitする。
- commitメッセージは対象リポジトリの規約と過去のcommitに合わせる。
- pre-commitのフックは飛ばさない。失敗したら原因を直す。
- ある修正が以前の修正を打ち消す内容になったら、その指摘を仕様の問題として持ち越す。修正と差し戻しの往復を止めるため。

## 繰り返し

(1)から(3)までを一巡とする。修正が1件でもあった巡の次は、(1)から始める。修正が1件も無い巡で繰り返しを終える。

2巡目以降は、前の巡の修正だけを対象にする。全体を読み直すと、毎回新しい細部が挙がり収束しないため。

- (1)と(3)は、前の巡の修正で変わった部分だけを検査する。
- (2)は、前の巡の問題が解消したかと、修正で新しく壊れた所が無いかだけを確かめさせる。

見送りや持ち越しと判定した指摘が再び挙がっても、修正には数えない。

## 完了処理

### 1. commitをまとめる

未pushのcommitが無ければ、この項と次の項を飛ばす。

`git log --reverse --format='%h %s' <開始commit>..HEAD`で未pushの全commitを読み、次の方針でまとめ方を決める。

- 同じ箇所や同じ主題の修正commitは一つにまとめる。主題が異なる修正は分けたまま残す。
- 開始時のHEADまでのcommitは、依頼者が分けた単位のまま残す。メッセージの名残を直すだけにとどめる。
- まとめた後のメッセージは、そのcommitの内容を言い表すものにする。レビューの巡や指摘には触れない。

rebaseは対話エディタを使わずに行う。まとめ方を書いたtodoファイルを作業用ディレクトリに作り、`GIT_SEQUENCE_EDITOR`で差し替える。

```bash
git rev-parse HEAD
GIT_SEQUENCE_EDITOR="cp <todoファイルのパス>" git rebase -i <開始commit>
```

1行目の出力がrebase前のHEADに当たる。後の確認で使うため控える。

todoファイルでは`pick`と`fixup`を使う。メッセージを変えるcommitは、`pick`の次の行に`exec git commit --amend -m "<新しいメッセージ>"`を置く。この形はメッセージ全体を置き換えるため、元のcommitにあった`Co-Authored-By:`などのtrailerは、`-m`をもう一つ足して書き写す。元のメッセージの全文は`git log -1 --format=%B <commit>`で読む。

rebaseが途中で止まったら、`git rebase --abort`で戻し、まとめずにpushへ進む。

rebaseの後、`git diff <rebase前のHEAD> HEAD`の出力が空であることを確かめる。空でなければ`git reset --hard <rebase前のHEAD>`で戻し、まとめずにpushへ進む。

まとめずにpushした場合、未pushのcommitのメッセージに残る名残は持ち越す。

### 2. pushする

- 対象リポジトリや実行環境にpush前の確認手順があれば、それに従う。
- `git push origin HEAD:<head branch>`でpushする。拒否されたら強制pushはせず、作業ツリーを残して報告する。

### 3. 片付ける

- 準備でdraftに戻していれば、`gh pr ready <PR番号>`で元に戻す。pushできなかった場合はdraftのまま残す。修正がremoteに無いままマージされるのを防ぐため。
- pushできたか、pushを飛ばした場合は、準備で作った作業ツリーを`git worktree remove <パス>`で消す。

### 4. 報告する

次の内容を依頼者へ伝えて終わりにする。

- pushしたcommitの一覧と、それぞれが直した内容
- 持ち越した指摘。仕様の問題、別のPRで対応すべきもの、commitのメッセージに残る名残
- 見送った指摘と、その理由
- 飛ばしたステップ、予定どおりに進まなかったこと、残した状態
- 依頼者の作業ツリーのbranchがremoteより遅れている場合は、その旨
- レビュアーがGitHubへ誤って投稿したコメントやreview
- 繰り返した巡の数と、各巡のレビュー結果の全文

## よくある取りこぼし

| 取りこぼし | 正しくは |
|---|---|
| 判定に迷って依頼者へ質問する | 根拠を順に探し、決まらなければ持ち越して報告する |
| 指摘を確かめずに事実として直す | 主張を確かめ、直す費用に見合うものだけを直す |
| 指摘を1件ずつ直し始める | 全件を並べ、同じ機能に集まったら機能ごと見直す |
| まれな経路の指摘に、条件を書き足して応える | 見送る。実行者が状況から判断できることは書かない |
| 2巡目以降も全体をレビューする | 前の巡の修正だけを対象にする |
| 複数の指摘を1commitで直す | 1件につき1commitにし、完了処理でまとめる |
| 巡の途中でpushする | pushは完了処理で一度だけ行う |
| レビュー対応の経緯をcommitメッセージに残す | commitの内容を言い表すメッセージにする |
| rebaseの後に内容の一致を確かめない | rebase前のHEADとの差分が空であることを確かめる |
| draftに戻したまま終える | 開始時の状態に戻す |
