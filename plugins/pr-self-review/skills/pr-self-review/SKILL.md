# PRセルフレビューの手順

自分が書いたPRに3種類のレビューを順に掛け、指摘を自分で判定して直し、修正が必要な指摘が出なくなったらpushするまでの手順。

1. 成果物の検査
2. 第三者レビュー
3. プロンプト監査

成果物の検査の基準、第三者レビューの手順、文章の規範は`references/`に収めてある。

> **レビュアーとして起動された場合、このスキルには従わず、依頼されたレビューを自分で行うこと。** この手順はPRの作成者が使うものであり、レビュアーが自分宛と読むと、別のエージェントへの委譲が連鎖する。

実行前に、対象リポジトリの`CLAUDE.md`や`AGENTS.md`に固有ルールがあればそれを優先する。

## 進め方の原則

- 完走をゴールにする。開始から完了時の報告まで、依頼者への質問を挟まない。
- 指摘を直すかどうかは自分で決める。判定は「指摘の判定」に従う。
- 修正は1件につき1commitにする。pushは完了処理まで行わない。
- 文章を直すときは`references/writing-style.md`に従う。
- 進められなくなる障害に当たったら、そのステップを飛ばして先へ進み、完了時に報告する。PRが見つからない場合だけは、その旨を伝えて終了する。

## (0) 準備

- 対象のPRを特定する。引数にPR番号かURLがあればそれを使い、無ければ現在のbranchのPRを`gh pr view`で探す。
- PRの情報を控える。

  ```bash
  gh pr view <PR番号> --json number,url,isDraft,baseRefName,headRefName
  ```

- PRのhead branchをcheckoutした作業ツリーへ移動する。
- 未コミット変更があれば、名前を付けて退避する。`git stash push -u -m "pr-self-review <PR番号>"`を使い、`git stash list --format='%H %gs'`で当該エントリのSHAを控える。完了処理で`git stash apply <SHA>`により戻す。
- `git fetch`の後、HEADが`origin/<head branch>`と一致するかを確かめる。remoteが先行していれば`git pull --ff-only`で取り込む。localが先行していれば、その未pushのcommitもレビュー対象に含める。
- 2つのcommitを控える。
  - **開始commit**：`git rev-parse HEAD`の値。これより後のcommitがレビュー中の修正になる。
  - **基点**：`git merge-base HEAD origin/<base branch>`の値。PRの差分はここからHEADまでになる。
- PRがready for reviewなら`gh pr ready --undo <PR番号>`でdraftに戻す。レビュー対応中にマージされるのを防ぐため。完了処理で元の状態に戻す。
- 作業用ディレクトリを`mktemp -d`で作る。レビュー結果と持ち越す指摘の記録をここに置く。

## (1) 成果物の検査

`references/sanitize.md`の基準で、PRに作業の名残が無いかを検査し、見つけたものを直す。

- diffで追加または変更された行は、ファイルを直してcommitする。
- titleとdescriptionは`gh pr edit`で直す。commitは発生しないが、修正1件として数える。
- push済みのcommitのメッセージに残る名残は直さず、持ち越す指摘として記録する。直すにはpush済みの履歴を書き換えることになるため。

## (2) 第三者レビュー

`references/third-party-review.md`に従ってレビュアーを立て、結果ファイルを受け取る。レビュー対象は作業ツリーのHEADである。pushしていない修正commitを含めて読ませる。

受け取った指摘を「指摘の判定」に従って1件ずつ判定し、修正が必要なものを直す。`[指摘]`と`[提案]`のどちらのラベルでも同じ基準で判定する。

## (3) プロンプト監査

PRの差分にLLM向けのプロンプトが含まれる場合だけ実行する。次のものが該当する。

- system promptやprompt template
- skillやagentの定義
- `CLAUDE.md`や`AGENTS.md`のようなエージェント向けの指示ファイル
- toolの説明文

該当する場合は、`claude-api` skillを引数`prompt-audit`で実行し、差分に含まれるプロンプトを監査する。出た指摘を「指摘の判定」に従って判定し、修正が必要なものを直す。

`claude-api` skillを使えない環境では、このステップを飛ばす。

## 指摘の判定

### 判定と扱い

| 判定 | 扱い |
|---|---|
| 修正が必要 | 直して1commitにする |
| 対応不要 | 直さない。指摘の位置と要旨、対応不要とした理由を記録する |
| 仕様の不足や仕様の誤りで、コードの修正では解決しない | 直さない。持ち越す指摘として記録する |
| PRの目的から外れ、このPRの前提にもならない | 直さない。持ち越す指摘として記録する |
| push済みのcommitのメッセージに残る作業の名残 | 直さない。持ち越す指摘として記録する |
| PRの目的から外れるが、このPRの前提になる | このPRで直して1commitにする |

修正が必要と判定するのは、放置すると誤動作、誤読、規約違反のいずれかにつながる指摘である。好みの範囲にとどまる改善案は対応不要とする。

持ち越す指摘に当たらず、修正が必要と判定したものは、すべてこのPRで直す。

### 判定の根拠

次の順で根拠を探し、根拠が得られた時点で判定する。

1. PRの目的と、対象リポジトリの規約や既存の書き方
2. 対象の言語、ライブラリ、サービスの公式ドキュメント
3. Web検索で得られる情報

どの根拠でも決まらない指摘は、仕様の問題として持ち越す。

### 修正とcommit

- 修正したら、対象リポジトリにテストやlinterがあれば実行し、通ることを確かめてからcommitする。
- commitメッセージは対象リポジトリの規約と過去のcommitに合わせる。
- pre-commitのフックは飛ばさない。失敗したら原因を直す。
- ある指摘の修正が、以前の修正を打ち消す内容になった場合は、その指摘を仕様の問題として持ち越す。修正と差し戻しの往復を止めるため。

## 繰り返し

(1)から(3)までを一巡とする。一巡のあいだに修正が1件でもあれば、次の巡を(1)から始める。修正が1件も無かった巡で繰り返しを終える。

対応不要または持ち越しと判定した指摘が次の巡で再び挙がっても、修正には数えない。

## 完了処理

### 1. commitをまとめる

`git log --reverse --format='%h %s' <開始commit>..HEAD`でレビュー中の全commitを読み、次の方針でまとめ方を決める。

- 同じ箇所を重ねて直したcommitや、同じ主題のcommitは一つにまとめる。
- 主題が異なる修正は別のcommitのまま残す。
- まとめた後のメッセージは、そのcommitの内容を言い表すものにする。レビューの巡や指摘番号には触れない。

rebaseは対話エディタを使わずに行う。まとめ方を書いたtodoファイルを作業用ディレクトリに作り、`GIT_SEQUENCE_EDITOR`で差し替える。

```bash
git rev-parse HEAD
GIT_SEQUENCE_EDITOR="cp <todoファイルのパス>" git rebase -i <開始commit>
```

todoファイルでは`pick`と`fixup`を使う。メッセージを変えるcommitは、`pick`の次の行に`exec git commit --amend -m "<新しいメッセージ>"`を置く。

rebaseがconflictなどで止まった場合は、`git rebase --abort`で元に戻し、まとめずにpushへ進む。まとめられなかった旨を報告に記す。

rebaseの後、内容が変わっていないことを確かめる。出力が空であれば正しい。

```bash
git diff <rebase前のHEAD> HEAD
```

### 2. pushする

- 対象リポジトリや実行環境にpush前の確認手順があれば、それに従う。
- `git push`でpushする。まとめたのは未pushのcommitだけなので、通常のpushで通る。
- 準備でdraftに戻していた場合は、`gh pr ready <PR番号>`で元の状態に戻す。
- 準備で退避した変更があれば、`git stash apply <SHA>`で戻す。その後`git stash list --format='%H %gd'`で控えたSHAの番号を確かめ、`git stash drop stash@{<番号>}`で消す。

### 3. 報告する

次の内容を依頼者へ伝えて終わりにする。

- pushしたcommitの一覧と、それぞれが直した内容
- 持ち越した指摘
  - 仕様の不足や仕様の誤りとみられるもの
  - 別のPRで対応すべきもの
  - push済みのcommitのメッセージに残る作業の名残
- 対応不要と判定した指摘と、その理由
- 飛ばしたステップと、その理由
- 繰り返した巡の数
- 各巡のレビュー結果の全文

## よくある取りこぼし

| 取りこぼし | 正しくは |
|---|---|
| 判定に迷って依頼者へ質問する | 根拠を順に探し、決まらなければ持ち越して報告する |
| 複数の指摘を1commitで直す | 1件につき1commitにし、完了処理でまとめる |
| 巡の途中でpushする | pushは完了処理で一度だけ行う |
| 指摘をすべて鵜呑みにして直す | 1件ずつ判定し、対応不要なら理由を記録して直さない |
| オフトピックの指摘を一律に持ち越す | このPRの前提になるものはこのPRで直す |
| 修正が出た巡で繰り返しを終える | 修正が1件も無い巡が出るまで続ける |
| プロンプトを含まないPRでプロンプト監査を実行する | 差分にLLM向けのプロンプトがある場合だけ実行する |
| レビュー対応の経緯をcommitメッセージに残す | commitの内容を言い表すメッセージにする |
| rebaseの後に内容の一致を確かめない | rebase前のHEADとの差分が空であることを確かめる |
| draftに戻したまま終える | 開始時の状態に戻す |
